# Стратегия тестирования портированного кода

## Цель

Тесты должны доказать три независимых свойства:

1. переписанный объект **создаётся** на Babelfish;
2. на одинаковых данных он **меняет состояние базы так же**, как оригинал на MS SQL;
3. при ошибочном входе он **ведёт себя так же**: тот же номер ошибки, тот же откат,
   то же состояние таблиц после.

Первое свойство доказывается компиляцией и **не доказывает ничего сверх себя** —
T-SQL допускает отложенное разрешение имён, процедура создаётся со ссылкой на
несуществующую таблицу. Второе и третье доказываются только запуском.

Портирование без теста считается незавершённым. Это инвариант 2 навыка,
и он согласован с правилом «Тесты — часть реализации» из `babelfish-compatibility`.

## Отличие от тестирования читающего пути

`babelfish-compatibility` тестирует **ответ** запроса: два движка вернули одно и то же.
Здесь тестируется **побочный эффект**: два движка одинаково изменили таблицы.

Отсюда разница в устройстве теста. Там достаточно сравнить результат вызова.
Здесь нужен снимок состояния до и после, а сам вызов результата может не возвращать вовсе.

## Обязательный минимум: три сценария

Порт, проверенный только на удачном пути, не готов. Три прогона обязательны.

### 1. Удачный путь

Вход, который задевает **все ветки** исходной конструкции. Для `MERGE` с двумя ветками
это минимум четыре строки:

- строка есть в цели и в источнике, данные совпадают → не должна измениться
- строка есть в обоих, данные разные → должна обновиться
- строка есть только в источнике → должна вставиться
- строка есть только в цели, если была ветка `WHEN NOT MATCHED BY SOURCE` → должна удалиться или обновиться

Проверка: снять состояние целевых таблиц до, выполнить на обоих движках с
одинаковым входом, снять после, сравнить построчно.

### 2. Идемпотентность

Тот же вход второй раз. `MERGE` был идемпотентен по построению; разложенный
`UPDATE` плюс `INSERT` — не обязательно. Дубли или повторный инкремент здесь
и всплывают.

Проверка: состояние после второго прогона совпадает с состоянием после первого.

### 3. Ошибка

Заведомо неверный вход: нарушение внешнего ключа, `NULL` в `NOT NULL`, дубль ключа.

Сравнивать три вещи:

- **номер ошибки** — важнее текста; текст у движков отличается всегда, а совпадение
  номера показывает, что маппинг ошибок и блок `CATCH` отработали одинаково
- **состояние таблиц после** — откат должен быть одинаковым
- **`RETURN`-код**, если процедура его отдаёт

## Краевые случаи, специфичные для пишущего пути

Каждый пункт найден на практике и стоил времени.

**Дубли в источнике.** `MERGE` при двух строках на один ключ падает с ошибкой 8672.
Разложенный `UPDATE ... FROM` молча берёт одну из них, недетерминированно.
Тест обязателен там, где уникальный ключ цели не страхует.

**Пустая строка против `NULL`.** Разные значения, которые легко смешать при
подготовке фикстуры. В боевых данных встречаются строковые `NOT NULL` колонки
с пустыми значениями — вставка `NULL` туда упадёт, и упадёт именно тест, а не порт.

**Хвостовые пробелы.** В MS SQL `'a' = 'a '` истина, в PostgreSQL для `varchar` — ложь.
Внутри Babelfish поведение MS SQL сохраняется, но фикстура, прошедшая через
`sqlcmd -W`, пробелы потеряет. Проверять через `DATALENGTH`, а не сравнением.

**`rowversion` и вычисляемые колонки.** Генерируются движком, у каждого свои.
Из сравнения исключать явно, иначе тест будет падать всегда.

**Регистр под CI-коллацией.** Если ключ соединения — строка, две записи,
различающиеся регистром, схлопнутся в одну. Фикстура должна это задевать.

## Оформление

Тест должен остаться в репозитории и прогоняться повторно, а не быть разовой
проверкой в консоли.

Минимальный комплект на процедуру:

```
tests/<схема>.<процедура>/
  fixture.sql     подготовка: очистка целевых таблиц и вставка исходного состояния
  input.sql       вызов процедуры с фиксированным входом
  state.sql       SELECT состояния целевых таблиц, с ORDER BY по ключу
  expected.txt    эталон, снятый с MS SQL
```

Прогон: применить `fixture` на обоих движках, выполнить `input`, снять `state`,
сравнить между движками и с `expected`.

`ORDER BY` в `state.sql` обязателен. Без него порядок строк не определён, и тест
будет мигать на ровном месте.

## Равные условия

Перед сравнением убедиться, что движки в одинаковом состоянии. Нарушение даёт
ложные расхождения, которые выглядят как дефекты движка и съедают день.

- **Проверки целостности.** Если на время загрузки фикстуры отключались внешние
  ключи, вернуть их до прогона. На Babelfish это `session_replication_role`,
  а не `NOCHECK CONSTRAINT ALL` — последний принимается без ошибки и не выполняется.
- **Данные.** Совпадают построчно, а не «примерно». Сверить `COUNT(*)` по всем
  задействованным таблицам до начала.
- **Коллация и режим.** Проверить `SERVERPROPERTY('Collation')` на обоих движках.

## Чего тест не докажет

Записывать в отчёт явно, а не умалчивать.

**Конкурентность.** Разложение `MERGE` на несколько операторов меняет атомарность.
Последовательный одиночный прогон слеп к этому по построению — как однопоточный
тест слеп к состоянию гонки. Нужен отдельный двухсессионный тест, и его отсутствие
надо называть, а не выдавать зелёный прогон за доказательство безопасности.

**Производительность.** Планы выполнения не сравниваются. Порт может быть
корректным и при этом на порядок медленнее.

**Полноту фикстуры.** Тест доказывает поведение на тех данных, что в нём есть.
Боевые данные содержат случаи, которых в фикстуре нет.

## Когда можно ставить вердикт

| Вердикт | Условие |
|---|---|
| `ПОРТИРОВАНО` | объект создан, три сценария совпали, краевые случаи покрыты, тест лежит в репозитории |
| `ПОРТИРОВАНО С ОГОВОРКАМИ` | то же, но есть расхождение — оно описано с указанием входа, при котором проявляется |
| `НЕ ПОРТИРУЕТСЯ` | блокер без известного обхода |

Прогон только удачного пути, ручная проверка без сохранённого теста и совпадение
одного лишь числа строк — ни одно из этого не даёт права на `ПОРТИРОВАНО`.
