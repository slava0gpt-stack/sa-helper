# PROBLEMS.md — база знаний по миграции `web` на Babelfish 5.4.0

Что это: справочник по проблемам конвертации боевой базы `web` (MS SQL Server 2017, билетная
платформа Ticketland) на Babelfish 5.4.0 — слой совместимости T-SQL поверх PostgreSQL.

Как пользоваться: получил ошибку — ищи по её тексту (`Ctrl+F` по номеру `Msg` или по фразе).
Заголовки разделов — это дословный текст ошибки движка или симптом.

Уровни уверенности проставлены в каждом разделе:

| Уровень | Что означает |
|---|---|
| **РЕШЕНО** | Рецепт применён на стенде, результат сверен с эталоном MS SQL. |
| **ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ** | Работает, но не так, как в MS SQL. Чем именно — написано в разделе. |
| **НЕ РЕШЕНО** | Что известно и куда копать. Ничего не приукрашено. |

Стенд, на котором всё замерено (`02_bench/docker-compose.yml`, поднимается `make bench`):

| Движок | Порт | Роль |
|---|---|---|
| MS SQL Server 2019 | `24333` | эталон |
| Babelfish 5.4.0 (TDS) | `21433` | цель проверки |
| Babelfish (PostgreSQL-порт) | `25433` | накат нативных функций через `psql` |
| PostgreSQL 18 | `25434` | контроль: что было бы при нативном переезде без Babelfish |

Где что лежит: исходники заблокированных процедур — `04_port/orig/`, переписанные —
`04_port/ported/`, нативные функции — `04_port/ported/native/`. В шапке каждого файла
в `ported/` расписано, что именно и почему изменено.

# Часть 0. Молчаливые изменения

Здесь то, что **работает и не даёт никакой ошибки**, но ведёт себя иначе, чем в MS SQL.
Никто не узнает об этом, пока не сломается в бою. Прочитать до, а не после.

## М1. Все 203 кластерных индекса стали некластерными, таблицы стали heap

**Уровень:** ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ.

**Симптом.** Ошибок нет. `CREATE ... CLUSTERED INDEX` проходит, объект создаётся.
Первичные ключи на месте: 227 из 227.

**Что на самом деле.** В PostgreSQL нет кластерных индексов в смысле MS SQL. Все 203
кластерных индекса стали обычными некластерными. Физического порядка строк в таблице нет,
таблицы — heap.

**Чем это бьёт.**
* Запросы, которые в MS SQL получали строки уже отсортированными «бесплатно» (сканирование
  кластерного индекса), на Babelfish получат их в произвольном порядке, если нет явного `ORDER BY`.
  Это одна из причин вердикта «порядок иной» в `06_compare/compare_results.py`.
* Range scan по ключу кластерного индекса больше не последовательный — планы и время другие.
  См. [Н5](#производительность-не-измерялась-вообще): это не измерялось.

**Что делать.** Проверить все запросы, которые полагаются на порядок без `ORDER BY`.
Их надо чинить в приложении, а не в базе.

## М2. Имена длиннее 63 символов молча превращаются в хеш

**Уровень:** ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ.

**Симптом.** Ошибок нет. Объект создан, но под другим именем.

**Причина.** Предел идентификатора в PostgreSQL — 63 байта. Babelfish обрезает и дописывает хеш.

**Пример из `web`:**

```
ix_performance_section_statistic_for_user__performance_id__min_price__max_price
  →  ix_performance_section_statistiff8a925a5a5038e8da83369c86021479
```

**Масштаб:** затронуты 7 внешних ключей и 1 индекс.

**Чем это бьёт.** Всё, что обращается к объекту по имени: скрипты обслуживания,
`ALTER TABLE ... DROP CONSTRAINT`, миграции, сравнение схем, мониторинг фрагментации.
Такой скрипт не найдёт объект и либо упадёт, либо тихо ничего не сделает.

**Что делать.** До миграции переименовать длинные имена в MS SQL, чтобы они укладывались
в 63 байта, — тогда имена по обе стороны совпадут.

## М3. rowversion генерируется движком заново, сохранённый watermark невалиден

**Уровень:** ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ.

**Симптом.** Ошибок нет. Колонка `rowversion`/`timestamp` есть, значения в ней есть.

**Что на самом деле.** Значения генерируются Babelfish заново, они никак не связаны
со значениями из MS SQL.

**Чем это бьёт.** На `rowversion` держатся дельта-фиды для внешних потребителей: потребитель
хранит watermark «я дочитал до 0x00000000000A1B2C» и после миграции этот watermark
не значит ничего. Возможны оба исхода — и пропуск изменений, и полная перевыгрузка.

**Что делать.** Найти всех потребителей дельта-фидов и согласовать сброс watermark
на момент переключения. Это организационная задача, техническим приёмом не закрывается.

## М4. Хинты принимаются и игнорируются, `UPDLOCK` больше не защищает

**Уровень:** ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ.

**Симптом.** `WITH (NOLOCK)`, `WITH (UPDLOCK)`, `OPTION (MAXDOP ...)`, `OPTION (RECOMPILE)`
принимаются парсером без ошибки. И не делают ничего.

**Причина.** В PostgreSQL нет табличных хинтов и хинтов оптимизатора. MVCC:
`READ UNCOMMITTED` ведёт себя как `READ COMMITTED`.

**Где безобидно.** `NOLOCK` — под MVCC читатель и так не блокирует писателя. Это чисто
декоративная конструкция после порта (см. [П11](#cant-mutate-an-internal-query-detected-multiple-mutations-on-the-same-position),
там `NOLOCK` пришлось убрать, и семантика не поменялась).

**Где ОПАСНО.** `UPDLOCK`. Классический паттерн «прочитал — проверил — записал»:

```sql
-- в MS SQL UPDLOCK держал строку и второй сессии приходилось ждать
SELECT @x = value FROM dbo.t WITH (UPDLOCK) WHERE id = @id;
IF @x IS NULL
    INSERT INTO dbo.t (id, value) VALUES (@id, @new);
ELSE
    UPDATE dbo.t SET value = @new WHERE id = @id;
```

На Babelfish блокировки нет — открывается окно гонки между `SELECT` и `INSERT`.
Два параллельных вызова могут оба увидеть «строки нет».

**Что делать.** Найти все `UPDLOCK` и переписать на приём, который работает в обоих движках:
уникальный индекс + перехват нарушения, либо явная транзакция с сериализуемым уровнем.
`MAXDOP`/`RECOMPILE` — просто удалить, они вводят читателя в заблуждение.

## М5. Три молчаливых изменения, у которых есть собственные разделы

* **`ALTER TABLE ... NOCHECK CONSTRAINT ALL` — молчаливая заглушка.** Принимается без ошибки
  и не выполняется. См. [П12](#msg-547--conflicted-with-the-foreign-key-constraint-при-загрузке-данных).
* **Разложенный `MERGE` при дублях в источнике молча берёт одну строку.** Это новый риск,
  созданный самим переписыванием. См. [П2](#msg-8672-attempted-to-update-or-delete-the-same-row-more-than-once).
* **`INFORMATION_SCHEMA` врёт про nullable.** См. [Н2](#information_schema-сообщает-not-null-колонку-как-nullable).

# Часть 1. Ошибки наката схемы и объектов

## `'MERGE' is not currently supported in Babelfish`

```
Msg 33557097, Level 16, State 1, Server BABELFISH
'MERGE' is not currently supported in Babelfish
```

**Уровень:** РЕШЕНО, рецепт проверен. Применён 41 раз.

**Симптом.** Падает **`CREATE PROCEDURE`**, а не выполнение. То есть процедура вообще
не создаётся, объект отсутствует.

**Причина.** `MERGE` не поддержан Babelfish **ни в одной версии** — проверено на 1.0–6.2.
Это не «пока не сделали в 5.4.0», ждать нечего.

**Решение — разложение на отдельные DML.**

| Ветка `MERGE` | Во что превращается |
|---|---|
| `WHEN MATCHED THEN UPDATE` | `UPDATE t SET ... FROM цель t INNER JOIN #src s ON <ON>` + предикат ветки в `WHERE` |
| `WHEN NOT MATCHED THEN INSERT` | `INSERT ... SELECT ... FROM #src s WHERE NOT EXISTS (SELECT 1 FROM цель t WHERE <ON>)` |
| `WHEN NOT MATCHED BY SOURCE THEN DELETE` | `DELETE FROM цель WHERE NOT EXISTS (SELECT 1 FROM #src s WHERE <ON>)` |
| `WHEN NOT MATCHED BY SOURCE THEN UPDATE` | отдельный `UPDATE` с тем же `NOT EXISTS` |

**Три правила, без которых разложение неэквивалентно:**

1. **Порядок веток: `UPDATE` → `BY SOURCE` → `INSERT`.** `INSERT` идёт последним, иначе
   только что вставленные строки попадут под другие ветки, чего `MERGE` не делает.
2. **Источник ОБЯЗАТЕЛЬНО материализовать** в `#temp` или табличную переменную **до**
   разложения. `MERGE` читает источник один раз; три раздельных DML иначе увидят три разных
   снимка. Особенно важно, когда источник — XML-шреддинг или подзапрос с джойнами.
3. **Явная проверка дублей** — см. [П2](#msg-8672-attempted-to-update-or-delete-the-same-row-more-than-once).
   Это отдельная ловушка, пропустить её нельзя.

**Пример** (`04_port/ported/import.region.sql`, ветки `MATCHED` + `NOT MATCHED`):

```sql
-- было: MERGE dbo.region AS t USING (...) AS s ON t.region_id = s.region_id
--       WHEN MATCHED AND t.[name] <> s.[name] THEN UPDATE SET t.[name] = s.[name]
--       WHEN NOT MATCHED THEN INSERT(region_id, [name]) VALUES(s.region_id, s.[name]);

-- 0. Материализация источника: шреддинг XML выполняется РОВНО ОДИН РАЗ, как в MERGE.
DROP TABLE IF EXISTS #region_src;
SELECT x.region_id                      AS region_id
     , CONVERT(NVARCHAR(250), x.[name]) AS [name]
  INTO #region_src
  FROM import.shred_region( CONVERT(VARCHAR(MAX), @import_subdata) ) AS x;

-- 1. Ветка MATCHED: ON → INNER JOIN, предикат ветки → WHERE.
UPDATE t
   SET t.[name] = s.[name]
  FROM dbo.region AS t
 INNER JOIN #region_src AS s ON t.region_id = s.region_id
 WHERE t.[name] <> s.[name];

-- 2. Ветка NOT MATCHED. Порядок колонок INSERT сохранён как в оригинале.
INSERT INTO dbo.region (region_id, [name])
SELECT s.region_id, s.[name]
  FROM #region_src AS s
 WHERE NOT EXISTS (SELECT 1 FROM dbo.region AS t WHERE t.region_id = s.region_id);
```

**Пример ветки `NOT MATCHED BY SOURCE`** (`04_port/ported/import.covid_restriction_obj.sql`):

```sql
-- Ветка WHEN NOT MATCHED BY SOURCE THEN DELETE (без доп. условия):
-- удаляются ВСЕ строки цели, которых нет в текущем источнике.
DELETE FROM dbo.covid_restriction
 WHERE NOT EXISTS (
       SELECT 1 FROM #src AS s
        WHERE dbo.covid_restriction.[covid_restriction_id] = s.[covid_restriction_id]
          AND dbo.covid_restriction.[obj_id]              = s.[obj_id] );
```

**Что НЕ надо трогать при порте.** На Babelfish 5.4.0 работают и оставлены дословно:
`TRY_CAST`, `CHECKSUM`, `FORMAT`, `STRING_AGG`, `JSON_VALUE`, `FOR JSON PATH`,
`CROSS APPLY`/`OUTER APPLY`, `SELECT ... INTO #temp`, `DROP TABLE IF EXISTS`,
табличные переменные, скалярные UDF. `CHECKSUM` самосогласован: его значения отличаются
от MS SQL, но сравниваются только между собой внутри одного оператора, поэтому предикаты
вида `CHECKSUM(s...) <> CHECKSUM(t...)` переносятся как есть.

**Цена.** 41 процедура, 5905 строк исходника → 8636 строк после порта. Оценка ручной
работы — 34 часа.

**Ограничение охвата.** Портирование процедур **не** покрывает 17 запросов с `MERGE` и XML,
которые идут в базу напрямую из приложения и джобов, минуя процедуры —
см. [Н6](#17-запросов-с-merge-и-xml-идут-в-базу-напрямую-минуя-процедуры).

## `Msg 8672 attempted to UPDATE or DELETE the same row more than once`

**Уровень:** РЕШЕНО, рецепт проверен. Защита добавлена в 8 процедур.

**Это самая опасная проблема в документе.** Ошибки после разложения не будет —
и в этом всё дело.

**Симптом.** В MS SQL при двух и более строках источника, попадающих на одну строку цели
по условию `ON`, `MERGE` падал с ошибкой 8672. После разложения (см. [П1](#merge-is-not-currently-supported-in-babelfish))
разложенный `UPDATE ... FROM` в той же ситуации **молча берёт одну из строк,
недетерминированно**. Данные тихо портятся.

**Причина.** Это не дефект Babelfish. Это риск, **созданный самим переписыванием**:
`UPDATE ... FROM` в T-SQL при неоднозначном соединении не ошибается по стандарту.

**Почему первичный ключ цели не спасает.** Уникальный ключ отобьёт только дубль на ветке
`INSERT` — когда строки в цели ещё нет. Самый опасный случай — **строка в цели уже есть,
и её обновляют два разных кандидата** — уникальным ключом не ловится вообще.
А это и есть основной сценарий повторного импорта.

**Решение: явная проверка дублей до всех DML.**

```sql
IF EXISTS ( SELECT 1
              FROM #performances
             GROUP BY performance_id, sale_channel_id   -- ключ = условие ON
            HAVING COUNT(*) > 1 )
    THROW 58672, '8672: duplicate rows in source #performances for ponominalu.performance (key: performance_id, sale_channel_id)', 1;
```

**КРИТИЧНО: `THROW`, а не `RAISERROR`.** Замерено на стенде:

| Конструкция | Обрывает батч в MS SQL | Обрывает батч в Babelfish 5.4.0 |
|---|---|---|
| Ошибка 8672 внутри процедуры | **да**, ни остаток процедуры, ни вызывающий батч не выполняются | — |
| `RAISERROR(..., 16, 1)` | **нет**, выполнение идёт дальше | **нет** |
| `THROW 58672, '...', 1` | **да** | **да** |

Буквальная замена 8672 на `RAISERROR` дала бы расхождение с оригиналом: после ошибки
процедура и вызывающий батч продолжили бы работу, чего в MS SQL не происходило.
Номер `58672 = 50000 + 8672` — `THROW` требует код `>= 50000`; исходный номер 8672
сохранён в начале текста сообщения, чтобы находилось поиском по логам.

**Оформление.** Проверку обернуть в `IF ... ELSE`, чтобы при срабатывании цель гарантированно
не была тронута ни одним DML.

**Точность условия проверки — выверена на эталоне MS SQL, а не угадана.**
Есть два варианта, выбирать осознанно.

*Вариант A — только источник* (`04_port/ported/ponominalu.job_ponominalu_repertoire_merge.sql`,
`import.tariff.sql`): `GROUP BY <ключ> HAVING COUNT(*) > 1` по `#src`. Проще, но срабатывает
чуть шире, чем MS SQL: ловит и те дубли, которые MS SQL пропустил бы.

*Вариант B — источник + цель + предикат ветки* (`04_port/ported/import.region.sql`):
срабатывает ровно там, где MS SQL давал 8672. Замеры на эталоне (`localhost,24333`):

| Ситуация | MS SQL |
|---|---|
| 2 строки источника на 1 строку цели, предикат ветки ложен у обеих | ошибки НЕТ |
| 2 строки источника, предикат истинен у обеих | **8672** |
| 2 строки источника, предикат истинен у одной | ошибки НЕТ |
| 2 строки источника, строки в цели нет | 2627 (нарушение PK) |

```sql
IF EXISTS ( SELECT 1
              FROM #region_src AS s
             INNER JOIN dbo.region AS t ON t.region_id = s.region_id  -- условие ON
             WHERE t.[name] <> s.[name]                               -- предикат ветки MATCHED
             GROUP BY s.region_id
            HAVING COUNT(*) > 1 )
    RAISERROR('8672: duplicate rows in source for dbo.region', 16, 1);
```

**Про `RETURN`-код.** Здесь три разных решения в трёх процедурах, потому что задачи разные:

* `THROW 58672` — когда важно оборвать батч (`ponominalu.job_ponominalu_repertoire_merge`);
* `RAISERROR(...)` внутри `TRY` — управление уходит в `CATCH`, `ERROR_NUMBER()` даст `50000`,
  а не `8672`. Это расхождение с оригиналом, оно задокументировано в шапке `import.region.sql`;
* флаг `@dup_in_source` + `RAISERROR` **за** `TRY` + `RETURN 8672` (`import.tariff.sql`) —
  когда важно вернуть вызывающему именно код 8672. Внутри `TRY` этого не сделать:
  `RAISERROR` severity 16 передал бы управление в `CATCH` и `RETURN` не выполнился бы.

**Вывод для нового порта.** Для каждого разложенного `MERGE` явно ответить: что должен увидеть
вызывающий при дублях — оборванный батч, код 50000 или код 8672? Ответ определяет конструкцию.

## `'XML NODES' is not currently supported in Babelfish`

```
Msg 33557097, Level 16, State 1
'XML NODES' is not currently supported in Babelfish
```

**Уровень:** РЕШЕНО, рецепт проверен. Создано 25 нативных функций, задействованы в 26 процедурах.

**Симптом.** Падает `CREATE PROCEDURE`.

**Причина и матрица поддержки XML-методов:**

| Метод | Babelfish |
|---|---|
| `.nodes()` | **не поддержан ни в одной версии** |
| `.query()` | **не поддержан ни в одной версии** |
| `.value()` | поддержан с **5.4.0** |
| `.exist()` | поддержан с **4.4.0** |

`.exist()` в процедурах `web` оставлен как был — он работает.

**Решение: вынести шреддинг в нативную PL/pgSQL-функцию поверх `xmltable()`.**

Функция создаётся в схеме `web_<схема>` (например `web_import`) и вызывается из T-SQL
как `<схема>.имя()` — Babelfish отображает эти пространства имён друг на друга.

Файл `04_port/ported/native/shred_region.sql`:

```sql
CREATE OR REPLACE FUNCTION web_import.shred_region(doc text)
RETURNS TABLE(region_id integer
            , name      text)
LANGUAGE plpgsql STABLE AS $function$
BEGIN
  -- Пустой/NULL документ -> пустая выборка, как .nodes() над пустым XML.
  IF doc IS NULL OR btrim(doc) = '' THEN
    RETURN;
  END IF;

  RETURN QUERY
    SELECT t.a_region_id::int
         , t.a_name
      FROM xmltable('/region/r'
                    PASSING XMLPARSE(DOCUMENT doc)
                    COLUMNS a_region_id text PATH '@basis_region_id',
                            a_name      text PATH '@name') AS t;
END $function$;
```

Вызов из T-SQL:

```sql
-- было:
--   FROM @import_subdata.nodes('/region/r') AS I(Q)
--        CROSS APPLY (SELECT i.q.value('@basis_region_id','int')   AS region_id
--                          , i.q.value('@name','nvarchar(250)')    AS [name]) AS x
SELECT x.region_id
     , CONVERT(NVARCHAR(250), x.[name])   -- повторяет усечение, которое делал .value(...,'nvarchar(250)')
  FROM import.shred_region( CONVERT(VARCHAR(MAX), @import_subdata) ) AS x;
```

**Четыре правила, иначе не заработает:**

1. **`LANGUAGE plpgsql`, НЕ `sql`.** См. [П4](#error-syntax-error-at-or-near-path) — это отдельная ловушка.
2. **Имена выходных колонок в нижнем регистре.** T-SQL-парсер Babelfish приводит идентификаторы
   к lower; колонка `regionId` из T-SQL не найдётся.
3. **Пустой/`NULL` документ → пустая выборка.** `.nodes()` над пустым XML возвращал ноль строк,
   а не ошибку. Без явной проверки `XMLPARSE` упадёт.
4. **Типы возвращать те же, что были в `.value()`,** а не типы колонки-приёмника.
   В `shred_region` это `::int` (как `.value('@basis_region_id','int')`), хотя `dbo.region.region_id`
   объявлен `numeric(9,0)`: в MS SQL значение сначала разбиралось как `int` внутри `USING`
   и лишь потом неявно приводилось при вставке. Так точка и текст ошибки переполнения
   остаются теми же. Строки возвращать как `text`, а усечение делать в вызывающей процедуре
   через `CONVERT(NVARCHAR(n), ...)`.

**Накат.** Нативные функции ставятся **не** через `sqlcmd`, а напрямую в PostgreSQL:

```sh
docker exec web-bbf psql -f /path/to/shred_region.sql
```

## `ERROR: syntax error at or near "PATH"`

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** Нативная функция-шреддер создалась без ошибок, а вызов её из T-SQL падает
с синтаксической ошибкой на слове `PATH` — при том что в тексте T-SQL-запроса никакого
`PATH` нет.

**Причина.** Функция была объявлена `LANGUAGE sql`. PostgreSQL инлайнит SQL-функции в план
вызывающего запроса; тело функции с `xmltable(... COLUMNS ... PATH ...)` попадает
в T-SQL-парсер Babelfish, который синтаксис `xmltable` не знает.

**Решение.** `LANGUAGE plpgsql` — тело не инлайнится, T-SQL-парсер его не видит.

```sql
-- НЕ ТАК:
CREATE OR REPLACE FUNCTION web_import.shred_region(doc text)
RETURNS TABLE(region_id integer, name text)
LANGUAGE sql STABLE AS $$ SELECT ... FROM xmltable(...) $$;

-- ТАК:
LANGUAGE plpgsql STABLE AS $function$ BEGIN RETURN QUERY SELECT ... FROM xmltable(...); END $function$;
```

## `FORMATMESSAGE` в Babelfish не поддержана

**Уровень:** РЕШЕНО, рецепт проверен. Встречается в 25 из 41 портированных процедур.

**Симптом.** Ошибка при создании процедуры. Практически всегда — в блоке `CATCH`,
где собирается диагностическое сообщение.

**Решение — конкатенация, дословно повторяющая формат.**

```sql
-- было: FORMATMESSAGE('ERROR_NUMBER = %d, ERROR_MESSAGE = %s, ERROR_PROCEDURE = %s, ERROR_LINE = %d',
--                      @ERROR_NUMBER, @ERROR_MESSAGE, @ERROR_PROCEDURE, @ERROR_LINE)
SELECT @MSG = 'ERROR_NUMBER = '     + ISNULL(CONVERT(VARCHAR(20), @ERROR_NUMBER), '')
            + ', ERROR_MESSAGE = '  + ISNULL(@ERROR_MESSAGE, '')
            + ', ERROR_PROCEDURE = '+ ISNULL(@ERROR_PROCEDURE, '')
            + ', ERROR_LINE = '     + ISNULL(CONVERT(VARCHAR(20), @ERROR_LINE), '');
```

**Не забыть `ISNULL`.** `FORMATMESSAGE` подставлял `NULL`-аргумент как пустое место,
а конкатенация с `NULL` даст `NULL` во всей строке — и сообщение об ошибке исчезнет целиком.
Именно тогда, когда оно нужнее всего.

**Разделители и пробелы копировать байт в байт** — по этим строкам сделаны алерты и грепы в логах.

## `RAISERROR` с числовым кодом — `sys.messages` в Babelfish нет

**Уровень:** ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ.

**Симптом.** `RAISERROR(52372, 16, 1)` — форма с номером сообщения из `sys.messages`.
В Babelfish этой таблицы нет.

**Решение — номер переносится в текст, `RETURN`-код не меняется:**

```sql
-- было: RAISERROR(52372, 16, 1)
RAISERROR('52372: NO DATA in /city/r', 16, 1);
RETURN 52372;   -- RETURN-код НЕ трогать: по нему принимает решение вызывающий
```

**Что изменилось.** `ERROR_NUMBER()` теперь вернёт `50000` вместо `52372`. Если вызывающий
код или джоб разбирает именно `ERROR_NUMBER()` — он сломается. Разбор текста сообщения
продолжит работать, потому что номер сохранён в начале строки.

**Что делать.** Проверить всех, кто ловит эти коды: `RETURN`-код сохранён и надёжен,
`ERROR_NUMBER()` — нет.

## Схема накатывается наполовину: 626 объектов из 1228

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** `deploy.py bbf` показывает сотни сбоев на `10_tables` и `15_constraints`.
На эталоне MS SQL те же файлы проходят целиком.

**Причина.** Четыре конструкции T-SQL, которые Babelfish по умолчанию отвергает,
но умеет игнорировать по явному разрешению.

**Решение — четыре «escape hatch»:**

```sql
EXEC sp_babelfish_configure 'escape_hatch_for_replication',            'ignore', 'server';
EXEC sp_babelfish_configure 'escape_hatch_rowversion',                 'ignore', 'server';
EXEC sp_babelfish_configure 'escape_hatch_nocheck_add_constraint',     'ignore', 'server';
EXEC sp_babelfish_configure 'escape_hatch_nocheck_existing_constraint','ignore', 'server';
```

**Эффект:** 626 объектов → **1169** из 1228.

**Три грабли:**

1. **Только через `sp_babelfish_configure`.** `ALTER SYSTEM` эти параметры не берёт —
   отвечает `cannot be changed`.
2. **Не переживают пересоздание контейнера.** В `Makefile` цель `bench` выставляет их
   заново после каждого `docker compose up`. Для боевой установки — прописывать
   в `postgresql.conf`, иначе после первого же рестарта накат схемы развалится.
3. **`escape_hatch_nocheck_*` = «игнорировать», а не «выполнить».** Именно отсюда растёт
   [П12](#msg-547--conflicted-with-the-foreign-key-constraint-при-загрузке-данных):
   `WITH NOCHECK` принят и не применён.

**Остаток.** После escape hatch не хватало 59 объектов: две таблицы
([П9](#таблица-не-создаётся-вычисляемая-колонка-с-getdate),
[П10](#тип-sysgeography-отсутствует-postgis-в-образе-нет)) и всё, что за них цеплялось.
После починки таблиц (`04_port/ported/_tables_fix.sql`), повторного наката ограничений
(`04_port/ported/_constraints_retry.sql`) и портирования процедур достигнуто **полное
совпадение с эталоном**: 239 таблиц, 210 вью, 323 процедуры, 4 триггера, 145 внешних ключей,
389 индексов.

## `Msg 556 cannot DROP TABLE "#..." because it is being used by active queries in this session`

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** Процедура с `#temp` внутри `BEGIN TRY` при `XACT_ABORT ON` и автокоммите:
при ошибке внутри `TRY` на выходе из процедуры падает удаление proc-scoped `#temp`.
Эта вторая ошибка **глушит `RAISERROR` из `CATCH` и теряет `RETURN`-код** — вызывающий
получает не то, что процедура пыталась ему сообщить.

**Решение.** Заменить `#temp` на табличную переменную. Тогда сообщение и `RETURN`-код
доходят до вызывающего корректно.

```sql
-- было: SELECT ... INTO #tariff_src FROM ...
DECLARE @tariff_src TABLE ( tariff_id      INT
                          , [name]         NVARCHAR(250)
                          , is_dynamic     BIT
                          , discount_type  INT
                          , discount_value INT );
INSERT INTO @tariff_src (...) SELECT ... FROM import.shred_tariff(...);
```

**Когда это важно.** Только если внутри `TRY` возможна ошибка и вызывающий разбирает
`RETURN`-код. В `import.city` тот же `#temp`-подход работает нормально.
Ориентир: если процедура возвращает осмысленные коды ошибок — брать табличную переменную.
Пример: `04_port/ported/import.tariff.sql`.

## Таблица не создаётся: вычисляемая колонка с `GETDATE()`

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** `CREATE TABLE` падает. Пример: `import.info`.

```sql
[duration_sec] AS (CASE WHEN stop_time IS NULL THEN datediff(second, start_time, getdate())
                        ELSE datediff(second, start_time, stop_time) END)
```

**Причина.** Выражение недетерминированное; PostgreSQL не допускает недетерминированные
выражения в `GENERATED`-колонках.

**Решение: таблица без вычисляемой колонки + представление с тем же выражением.**

```sql
CREATE TABLE [import].[info] (
    [task_name]  VARCHAR (200)  NOT NULL,
    [info]       NVARCHAR (MAX) NOT NULL,
    [task_state] VARCHAR (50)   NOT NULL,
    [start_time] DATETIME       NOT NULL,
    [stop_time]  DATETIME       NULL,
    [task_xml]   XML            NULL,
    CONSTRAINT [PK_import_info] PRIMARY KEY CLUSTERED ([task_name] ASC)
);
GO
CREATE VIEW [import].[info_with_duration]
AS
SELECT i.[task_name], i.[info], i.[task_state], i.[start_time], i.[stop_time], i.[task_xml]
     , CASE WHEN i.[stop_time] IS NULL
            THEN DATEDIFF(SECOND, i.[start_time], GETDATE())
            ELSE DATEDIFF(SECOND, i.[start_time], i.[stop_time])
       END AS [duration_sec]
FROM [import].[info] AS i;
```

**Почему это эквивалентно.** Исходная колонка была **НЕ persisted** — она и так вычислялась
при каждом чтении. Семантика идентична.

**Условие применимости.** Если колонка была `PERSISTED` — приём не годится: там значение
физически хранилось и было зафиксировано на момент записи, а вью пересчитает его заново.

**Что поменять в приложении.** Кому нужен `duration_sec` — читает из
`import.info_with_duration`, а не из `import.info`.

Файл: `04_port/ported/_tables_fix.sql`.

## Тип `sys.geography` отсутствует, PostGIS в образе нет

**Уровень:** ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ.

**Симптом.** `CREATE TABLE [dbo].[subdomain]` падает на колонке
`[subdomain_coord] [sys].[geography] NULL`; следом не создаётся
`CREATE SPATIAL INDEX ... USING GEOGRAPHY_GRID`.

**Причина.** Типа `sys.geography` в этой сборке Babelfish нет, PostGIS в образе тоже
отсутствует — `pg_available_extensions` пуст.

**Решение — хранение координаты строкой в формате WKT:**

```sql
[subdomain_coord] VARCHAR (200) NULL,   -- было sys.geography, хранится как WKT
```

**Что теряется.** Все пространственные операции: `STDistance`, `STIntersects`, spatial-индекс.
Данные сохраняются полностью, вычислять по ним нельзя.

**Почему это приемлемо именно здесь.** В корпусе боевых запросов — **0 вхождений**
пространственных операций по этой колонке. Проверено по `web.sql` и по нарезке Query Store.
Если операции понадобятся — ставить PostGIS и менять тип на `geography`.

Файл: `04_port/ported/_tables_fix.sql`.

## `Can't mutate an internal query: detected multiple mutations on the same position`

```
Msg 33557097, Level 16, State 1, Server BABELFISH
Can't mutate an internal query: detected multiple mutations on the same position
```

**Уровень:** **НЕ РЕШЕНО.** Причина локализована, обход применён — **но результат
не верифицирован запуском.**

**Симптом.** Падает `CREATE PROCEDURE`, до какого-либо выполнения.
Затронуты `dbo.direct_ad_show_data_v2` и `dbo.direct_ad_stage_data_v1`.
`MERGE` в этих процедурах нет. В документированных ограничениях Babelfish этого случая нет.

**Что известно — минимальный воспроизводящий фрагмент** (нарезан пополам и накатан на стенд):

```sql
CREATE PROCEDURE dbo.zz AS BEGIN
  SELECT (SELECT perf.performance_full_url
          FROM st_show_performances AS perf WITH (NOLOCK)   -- <<< хинт
          WHERE perf.show_id = 1
          FOR XML PATH (''), TYPE).value('.', 'nvarchar(max)') AS perfs
END
```

Ломается сочетание **двух вещей в ОДНОМ подзапросе**:
(а) табличный хинт `WITH (NOLOCK)` / `WITH (READUNCOMMITTED)` и
(б) обёртка `( ... FOR XML PATH(''), TYPE ).value('.', 'nvarchar(max)')`.

**Что проверено по отдельности и работает** (то есть само по себе не блокер):

| Конструкция | Результат |
|---|---|
| `WITH (NOLOCK)` в обычном запросе | ОК |
| `WITH (NOLOCK)` + `FOR XML PATH(''), TYPE` **без** `.value(...)` | ОК |
| `FOR XML PATH(''), TYPE` + `.value(...)` **без** хинта | ОК |
| `TOP 4` / `ORDER BY` / `STUFF` / `CAST` / вложенный скалярный подзапрос внутри `FOR XML` | ОК |
| Хинт, спрятанный в производную таблицу `(SELECT * FROM t WITH (NOLOCK)) AS x` внутри `.value()`-подзапроса | **ВСЁ РАВНО ЛОМАЕТСЯ** |
| Достаточно **одного** хинта внутри `.value()`-подзапроса | **ПАДАЕТ 33557097** |

**Предполагаемая причина** (гипотеза по наблюдениям, не подтверждение из исходников Babelfish):
Babelfish переписывает текст T-SQL-запроса патчами по позициям в строке — табличные хинты
вырезает, а `(подзапрос FOR XML ...).value(...)` разворачивает в свою внутреннюю форму.
Когда оба патча приходятся на один подзапрос, регистрируются две мутации на одну позицию
и рерайтер аварийно останавливается.

**Применённый обход.** Убран **только** хинт `WITH (NOLOCK)` внутри `.value()`-подзапроса.
Остальные `WITH (NOLOCK)` в этих процедурах оставлены как были.
Семантика не меняется: Babelfish табличные хинты всё равно игнорирует
(см. [М4](#м4-хинты-принимаются-и-игнорируются-updlock-больше-не-защищает)),
то есть хинт в этом месте и до порта был декоративным.

**Чего НЕ сделано и почему уровень «не решено».** Обе процедуры не запускались и результат
их работы не сверялся с эталоном MS SQL. Известно только, что блокер локализован
и что после снятия хинта конструкция создаётся. Это не то же самое, что «работает».

**Куда копать.** Проверить накат и прогон обеих процедур на стенде; сравнить вывод
с эталоном на одинаковых данных. Отдельно — прогнать весь корпус запросов на предмет
других сочетаний «хинт + `.value()` над `FOR XML`»: раз ограничение недокументированное,
оно наверняка есть и в других местах.

Файлы: `04_port/ported/dbo.direct_ad_show_data_v2.sql`, `04_port/ported/dbo.direct_ad_stage_data_v1.sql`.

# Часть 2. Ошибки загрузки данных

## `Msg 547 ... conflicted with the FOREIGN KEY constraint` при загрузке данных

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** Срез данных грузится в MS SQL и падает на Babelfish конфликтами внешних ключей —
хотя перед загрузкой выполнено `ALTER TABLE ... NOCHECK CONSTRAINT ALL` и ошибок оно не выдало.

**Причина — молчаливая заглушка.** Babelfish принимает `ALTER TABLE ... NOCHECK CONSTRAINT ALL`
**без ошибки и не выполняет**. Внешние ключи остаются включёнными. Это следствие
`escape_hatch_nocheck_*` = `ignore` (см. [П7](#схема-накатывается-наполовину-626-объектов-из-1228)):
«игнорировать» здесь значит «принять и ничего не сделать».

**Решение — отключать проверки на уровне PostgreSQL:**

```sql
ALTER DATABASE babelfish_db SET session_replication_role = 'replica';
-- ... загрузка среза ...
ALTER DATABASE babelfish_db RESET session_replication_role;
```

**ОБЯЗАТЕЛЬНО вернуть `RESET` перед любым сравнением движков.** Иначе MS SQL проверяет
ограничения, а Babelfish нет — движки в неравных условиях, и сравнение врёт. Проверено:
это уже давало **ложное расхождение**, на разбор которого ушло время.

**Почему проверки вообще снимаются.** Срез данных связный, но не полный: часть родительских
строк лежит вне выборки (17 таблиц из 239). Это осознанное свойство стенда, а не дефект.

Код загрузки: `05_data/load_data.py`.

## `Msg 515 Cannot insert the value NULL into column ...` — пустая строка это не `NULL`

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** Загрузка падает на `NOT NULL` строковых колонках либо — что хуже — проходит,
но в двух движках оказываются разные значения, и последующее сравнение показывает расхождения.

**Причина.** В `web` есть `NOT NULL` строковые колонки с пустыми значениями: например
28 имён из одних пробелов в `dbo.obj`. При выгрузке `sqlcmd -W` обрезает пробелы,
и пустая строка внешне неотличима от `NULL`. Если при загрузке их смешать — данные разъедутся.

**Решение — различать явно.** В выгрузке `NULL` записан литералом `NULL`, пустая строка —
пустым полем:

```python
def lit(v, typ):
    # ВАЖНО: пустая строка и NULL — РАЗНОЕ.
    if v == "NULL":
        return "NULL"
    if v == "":
        return "NULL" if typ in NUM else "N''"   # для строк — именно пустая строка
    if typ in NUM:
        return v if re.fullmatch(r"-?\d+(\.\d+)?", v) else "NULL"
    return "N'" + v.replace("'", "''") + "'"
```

**Смежный приём из `load_data.py`.** Если батч `INSERT` упал — вставлять построчно, чтобы
потерять только реально сбойные строки, а не весь пакет. Иначе движки разойдутся по составу
данных, и все дальнейшие сравнения бессмысленны.

## `Msg 273` / `Msg 271` — запись в `timestamp`/`rowversion` или вычисляемую колонку

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** Загрузка падает при попытке записать колонку типа `timestamp`/`rowversion`
или вычисляемую.

**Причина.** Писать в них нельзя. Но в выгрузке, сделанной через `SELECT *`,
их значения **присутствуют** — позиции в файле заняты.

**Решение.** Позиции колонок в файле **сохранять** (иначе разбор строки по разделителю
съедет), а сами колонки **исключать** из списка вставки. В `load_data.py` это разделение
`allc` (все колонки в порядке файла) и `use` (подмножество, в которое реально пишем):

```python
# all = колонки в порядке файла; use = подмножество, в которое реально пишем
use = [(i, c, t) for i, (c, t, w) in enumerate(allc) if w]   # w = writable
...
if len(parts) != len(allc):   # сверяем с ПОЛНЫМ числом колонок, включая неписуемые
    skipped += 1; continue
vals = [lit(parts[i].strip(), t) for i, c, t in use]
```

**Дополнительно.** Загруженные значения `rowversion` всё равно не переживут миграцию —
см. [М3](#м3-rowversion-генерируется-движком-заново-сохранённый-watermark-невалиден).

## Колонки при загрузке перемешались: одноимённые таблицы в разных схемах

**Уровень:** РЕШЕНО, рецепт проверен.

**Симптом.** Данные загрузились «не в те» колонки. Ошибок может не быть вообще, если типы
совпали, — тогда это обнаруживается уже на сравнении результатов.

**Причина.** В `web` есть одноимённые таблицы в разных схемах: `city`, `performance`, `show` —
каждая в 2–3 схемах. При чтении метаданных сортировка только по имени таблицы смешивает
колонки разных таблиц в одну последовательность.

**Решение.** При чтении метаданных сортировать **по схеме И имени**, а ключом словаря
использовать полное имя `схема.таблица` в нижнем регистре.

# Чек-лист перед сравнением движков

Любое сравнение MS SQL и Babelfish достоверно только при равных условиях. Если хоть один
пункт не выполнен — расхождение может оказаться артефактом стенда, а не разницей движков.
Так уже было: невозвращённый `session_replication_role` дал ложное расхождение
и съел время на разбор.

**Схема**

* [ ] Четыре `escape_hatch` выставлены **через `sp_babelfish_configure`** и живы прямо сейчас
      (не переживают пересоздание контейнера — `make bench` их выставляет заново; после
      ручного `docker compose restart` проверить отдельно). См. [П7](#схема-накатывается-наполовину-626-объектов-из-1228).
* [ ] `deploy.py mssql` и `deploy.py bbf` дают одинаковый список объектов: 239 таблиц,
      210 вью, 323 процедуры, 4 триггера, 145 FK, 389 индексов.
* [ ] Нативные функции-шреддеры накатаны в схемы `web_<схема>` через `psql`
      (`sqlcmd` их не поставит). См. [П3](#xml-nodes-is-not-currently-supported-in-babelfish).
* [ ] Портированные процедуры накатаны на Babelfish (`make port`) — и **не** накатаны
      на эталон MS SQL: на эталоне должны остаться оригиналы, иначе сравнивается порт с портом.

**Данные**

* [ ] Оба движка загружены из **одних и тех же** файлов среза.
* [ ] Число строк совпадает по каждой таблице (ориентир: 73 403 строки всего).
* [ ] Пустые строки не превратились в `NULL` ни в одном движке.
      См. [П13](#msg-515-cannot-insert-the-value-null-into-column--пустая-строка-это-не-null).
* [ ] Строки, потерянные при построчной догрузке после сбоя батча, **потеряны в обоих
      движках одинаково** — иначе состав данных разный.

**Равные условия — самое важное**

* [ ] **`session_replication_role` возвращён в норму на Babelfish:**
      `ALTER DATABASE babelfish_db RESET session_replication_role;`
      Проверить фактически, а не «мы вроде выполняли».
      См. [П12](#msg-547--conflicted-with-the-foreign-key-constraint-при-загрузке-данных).
* [ ] Внешние ключи включены и с той, и с другой стороны. Помнить, что
      `ALTER TABLE ... CHECK CONSTRAINT ALL` на Babelfish — заглушка, состояние проверять
      запросом к каталогу, а не по факту успешного выполнения команды.
* [ ] `IDENTITY_INSERT` выключен везде, куда его включали при загрузке.

**Интерпретация результата**

* [ ] Разный **порядок** строк без `ORDER BY` — это не расхождение данных. Причина известна:
      кластерных индексов нет ([М1](#м1-все-203-кластерных-индекса-стали-некластерными-таблицы-стали-heap)),
      плюс другая сортировка кириллицы. `compare_results.py` различает
      «идентично» / «порядок иной» / «ДАННЫЕ РАЗЛИЧАЮТСЯ» намеренно — не схлопывать эти вердикты.
* [ ] Пустой результат в обоих движках — это «нет данных», а не «совпало».
      `compare_queries.py` помечает такой случай отдельно; не засчитывать его как успех.
* [ ] Расхождение по `ERROR_NUMBER()` там, где был `RAISERROR` с числовым кодом, —
      ожидаемо (`50000` вместо исходного). См. [П6](#raiserror-с-числовым-кодом--sysmessages-в-babelfish-нет).
* [ ] Значения `CHECKSUM` между движками **не** сравнивать: функция самосогласована внутри
      движка, но её значения различаются. Сравнивать только результат предиката.
* [ ] Значения `rowversion` между движками **не** сравнивать.
      См. [М3](#м3-rowversion-генерируется-движком-заново-сохранённый-watermark-невалиден).
* [ ] Каждое расхождение либо объяснено, либо занесено в этот файл. «Потом разберёмся»
      превращается в инцидент на проде.
