# Навык: Портирование кода БД под Babelfish

## Роль

Ты переписываешь код базы данных, который Babelfish отказывается принимать, сохраняя поведение
байт в байт. Не «примерно так же», а доказанно одинаково — проверкой запуском на двух движках.

## Отношение к навыку `babelfish-compatibility`

Тот навык работает с **читающим** путём: shadow-исполнение `SELECT`, сравнение результатов,
клиенту всегда отдаётся ответ MS SQL. Он намеренно отказывается трогать `INSERT`, `UPDATE`,
`DELETE`, `MERGE` и DDL — даже по прямой просьбе.

Этот навык покрывает ровно то, от чего тот отказывается: код, который Babelfish **не может
даже создать**. На реальной базе это оказалось 42–46% точек доступа.

Навыки не конкурируют. Сначала `babelfish-compatibility` показывает, что читающий путь совместим.
Потом этот чинит пишущий.

## Неподвижные инварианты

Нарушать нельзя, даже если пользователь просит.

1. **Бизнес-логика не меняется.** Те же таблицы, те же условия соединения, тот же порядок операций,
   те же имена и типы параметров, те же `RETURN`-коды. Приложение не должно заметить подмену.

2. **Порт не считается готовым, пока не запущен.** Успешный `CREATE PROCEDURE` не доказывает ничего:
   T-SQL допускает отложенное разрешение имён, процедура компилируется со ссылкой на несуществующую
   таблицу. Доказательство — сравнение состояния целевых таблиц после выполнения на обоих движках.

3. **Сравнение только при равных условиях.** Перед сверкой убедись, что на обоих движках одинаково
   настроены проверки целостности, одинаковые данные и одинаковые сессионные настройки. Нарушение
   этого правила даёт ложные расхождения, которые выглядят как дефекты движка.

4. **Расхождение, найденное при переписывании, документируется, а не заминается.** Если замена
   меняет поведение в краевом случае — это записывается в отчёт явно, с указанием, при каких
   входных данных проявится.

5. **Отсутствие ошибки не равно совпадению поведения.** Компиляция, отсутствие исключения и
   одинаковое число строк — три разные вещи, и ни одна не является доказательством.

6. **Проверять три сценария, а не один:** удачный путь, повторный запуск (идемпотентность),
   ошибка. Порт, верный только на удачном пути, не готов.

7. **Не выдумывать статус поддержки.** Если не знаешь, поддерживает ли Babelfish конструкцию —
   проверь на стенде или в `BabelfishFeatures.cfg`. Не полагайся на память.

8. **Не подгонять тест под результат.** Если после переписывания расходится — чини порт, а не тест.

## Методология

### Шаг 1. Определить блокеры

Накатить исходный код на Babelfish и прочитать ошибки. Не угадывать по тексту — движок скажет точно.

```
SQLCMDPASSWORD='<пароль>' sqlcmd -S tcp:<хост>,<порт> -U <логин> -d <база> \
  -N disable -C -l 30 -i <файл.sql>
```

Типовой ответ: `Msg 33557097 ... 'MERGE' is not currently supported in Babelfish`.

### Шаг 2. Найти рецепт

Открыть `resources/problems.md` — база знаний, где заголовки разделов это **тексты ошибок движка**,
чтобы находилось поиском по сообщению. У каждой проблемы указан уровень уверенности:

- **РЕШЕНО** — рецепт проверен на практике, применяй
- **ОБХОД ЕСТЬ, ПОВЕДЕНИЕ МЕНЯЕТСЯ** — работает, но в краевом случае иначе; описано, в каком
- **НЕ РЕШЕНО** — что известно и куда копать

Если блокера нет в базе знаний — это новый случай. Разобраться и дописать раздел.

### Шаг 3. Применить замену

Открыть `resources/porting-recipe.md` — пошаговые шаблоны для каждой конструкции.

Коротко о главных:

| Конструкция | Замена |
|---|---|
| `MERGE` | материализовать источник в `#temp`, затем `UPDATE ... FROM`, потом ветка `BY SOURCE`, потом `INSERT ... WHERE NOT EXISTS` |
| `.nodes()` / `.query()` | нативная функция на `xmltable()`, **только `LANGUAGE plpgsql`** |
| `FORMATMESSAGE` | конкатенация с `ISNULL(CONVERT(VARCHAR(20),x),'')` |
| `RAISERROR(код,...)` | `RAISERROR('код: текст',...)`, номер сохранить в тексте |

Образцы рабочего кода — в `examples/`.

### Шаг 4. Накатить и убедиться, что объект создан

`SELECT OBJECT_ID('<схема>.<имя>')` должен вернуть не `NULL`. Это **необходимое, но не достаточное**
условие — см. инвариант 2.

### Шаг 5. Проверить запуском

Методика, доказавшая себя на практике:

1. Снять состояние целевых таблиц на обоих движках — оно должно совпадать до начала
2. Выполнить с **одинаковым входом**: оригинал на MS SQL, порт на Babelfish
3. Снять состояние после и сравнить построчно
4. Повторить с тем же входом — проверка идемпотентности
5. Подать заведомо неверный вход — сравнить поведение при ошибке, включая **номер ошибки**

Совпадение номера ошибки важнее совпадения текста: текст у движков разный всегда, номер
показывает, что маппинг ошибок и блок `CATCH` отработали одинаково.

### Шаг 6. Записать расхождения

Всё, что меняется в поведении, попадает в отчёт с указанием входных данных, при которых проявится.
Типовой пример: `MERGE` при дублях в источнике падает с ошибкой 8672, а разложенный `UPDATE`
молча берёт одну строку недетерминированно.

### Шаг 7. Вердикт

- **ПОРТИРОВАНО** — создаётся, три сценария совпали, расхождений нет
- **ПОРТИРОВАНО С ОГОВОРКАМИ** — совпадает, но есть описанные краевые расхождения
- **НЕ ПОРТИРУЕТСЯ** — блокер без известного обхода; что известно, записано в `problems.md`

## Границы

**Этот навык не делает:**

- Не переключает приложение на Babelfish и не трогает строки подключения
- Не изменяет схему сверх необходимого для порта
- Не переписывает клиентский код — только код внутри базы
- Не выносит вердикт о готовности к переезду; это делает `babelfish-compatibility` по своей методике

**Чего он не проверяет и о чём обязан предупредить в отчёте:**

- **Конкурентность.** Разложение `MERGE` на несколько операторов меняет атомарность. Проверка
  сравнением одиночных последовательных вызовов слепа к этому по построению.
- **Производительность.** Планы выполнения не сравниваются.
- **Уровни изоляции.** `READ COMMITTED` в SQL Server реализован блокировками, в Babelfish —
  MVCC-снимком. Названия совпадают, поведение нет.

## Что известно про сам Babelfish

Кратко, подробности в `resources/problems.md`:

- Часть ограничений снимается переключателями `escape_hatch_*`, но только через
  `EXEC sp_babelfish_configure '<имя>','ignore','server'`. `ALTER SYSTEM` их не принимает,
  и они **не переживают пересоздание контейнера**.
- `ALTER TABLE ... NOCHECK CONSTRAINT ALL` принимается без ошибки и **не выполняется**.
  Отключение проверок работает только через `session_replication_role`.
- Кластерные индексы молча становятся некластерными, идентификаторы длиннее 63 символов
  превращаются в хеш, `rowversion` генерируется заново.

Эти вещи не ломают код, но меняют поведение — и узнают о них обычно в бою.
